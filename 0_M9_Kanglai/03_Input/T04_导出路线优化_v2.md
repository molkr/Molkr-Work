# 历史会话导出技术路线 v2（优化版，送 AC 审）

> 出具：T04 会话模块（91A）｜2026-11-08
> 缘起：T04 双源实战（DeepSeek 官方导出 54 会话 + ChatGPT .ai-chat-flow 捕获 12 会话）跑通后反推的路线优化。**本文自包含**——AC 无本地文件访问权，所需背景全部内嵌。
> 请求：AC 从平台能力知情者角度审三件事（见 §六），可推翻、可补充、可给替代方案。

## 一、背景：记忆库为什么要导出会话

摩氪记忆库（P001）的目标是「可检索/自生长/越来越懂你」。技术路线定为四层：**L1 原始导出（永不修改）→ L2 段卡/会话卡（AI 逐块提炼）→ L3 实体与主题聚类 → L4 沉淀偏好**，全部投影可从 L1 重算（AI 升级=重算投影全库受益）。目前 L2 双源已落成：DeepSeek 54 会话（51MB 官方导出 conversations.json）+ ChatGPT 12 会话（浏览器捕获 raw.json），合计 207 段卡/66 会话卡，检索库 FTS+bge-m3 向量双路可用。

## 二、现状两条路线与痛点（实战反推）

### 路线 A：官方账号级全量导出（DeepSeek 实用中）
流程：设置→数据管理→导出所有对话→等通知→ZIP 链接下载（24h 有效）→ conversations.json（全量）。
痛点：
1. **无增量**——每次导出都是全量，会话越多包越大（DeepSeek 51MB@54 会话，一年后可能 200MB+）；
2. **等待不可控**——官方处理最长 7 天，无法按需触发；
3. **手动触发**——靠人记得导，忘记则记忆库断粮；
4. ZIP 链接 24h 过期，错过要重来。

### 路线 B：浏览器单会话捕获（.ai-chat-flow 工具，ChatGPT 12 会话现状）
流程：工具在浏览器逐会话捕获→导出 capture 包装 raw.json（{capture, payload:{mapping, current_node,…}}）+衍生 MD/PDF。
痛点：
1. **单会话手工逐个**——12 个会话点了 12 次，规模化不可行；
2. **衍生层与 L1 混居**——MD/PDF/工具状态（.ai-chat-flow）与 raw.json 同目录树，分层被污染；
3. **文件名不含稳定 ID**——「标题 (1)__随机后缀.raw.json」，与 payload.conversation_id 对齐靠解析（T04G 实测标题重复 "(1)(2)(3)" 三份，靠 ID 才去重）；
4. **capture 包装**多一层（可接受但不规范）；
5. **无对账**——哪些会话已捕获、哪些新增，靠人眼；
6. **附件与多模态捕获完整性未验证**（图片/Canvas 是否进 parts）。

### 共同缺口
无统一收件箱与对账协议；无自动触发；命名/ID/落位无规范；两条路线各自为政，记忆库侧要写两套适配器（已写，但捕获侧乱投影侧就得猜）。

## 三、v2 路线设计（四层职责重划）

### 3.1 分层原则（对齐已固化的「底账不动、元数据可再生」）
- **L1 捕获层（唯一事实源）**：只进不改，文件名带平台+稳定 ID，与衍生层物理隔离。
- **L1.5 校验层（新增）**：收件箱→对账→放行，杜绝未登记数据混入。
- **投影层（已建成，零改动）**：chunker→map→reduce→index 全部沿用，只按平台分发适配器。
- **衍生层退役**：MD/PDF 转换不再作为流程环节（投影已由 T04 管线承担），仅按需人工生成。

### 3.2 统一捕获规范
- 文件名：`{平台}_{conversation_id 前 8 位}__{标题}.raw.json`（ID 进文件名，标题只作人读）；
- 落位：两平台统一落 `90_Inbox/` 待验区（按平台分子目录），**不直接进正式 input**；
- 内容：保持官方/捕获原生结构，不做格式改写（capture 包装允许存在，适配器已兼容）。

### 3.3 对账协议（新增，复用已建成的 t04_ingest 思路）
```
扫描 90_Inbox → 识别平台与 conversation_id → 对照 l1_registry（主键=平台+conversation_id）
  ├─ 新会话     → 整会话入管线
  ├─ updated_at 变新 → 尾部增量（已实现）
  ├─ 未变       → 跳过
  └─ 放行：Inbox 文件移入正式 input/ 并登记（移动非复制，Inbox 清零）
```
- registry 主键升格为「平台+conversation_id」，文件名降级为展示层——呼应 M91B 已固化的「稳定 ID 不依赖显示名或文件路径」决策。
- 对账命令一条：`t04_ingest.py --scan`（已支持按目录扫，扩展平台字段即可）。

### 3.4 触发策略（按平台能力分治）
| 平台 | 权威全量（低频） | 增量补充（高频） |
|---|---|---|
| DeepSeek | 官方导出，月度或里程碑事件手动触发 | 无官方增量——全量导出后靠对账只处理增量（已实现，包大但频率低可接受） |
| ChatGPT | 官方 Export data，月度（处理最长 7 天，当月度快照用） | 单会话捕获按需（重要对话聊完即捕） |

- 记忆：**全量导出当「月度快照保险」，单会话捕获当「热点增量」**——两条路线从互斥变互补。
- 自动化边界：ZCode 闲时任务可自动跑「对账+入库投影」（读本地文件属 AG 职责）；**导出动作本身留在人手**（涉及账号操作，且 AG 不得擅自拉起浏览器类 GUI——既有纪律）。

### 3.5 附件与多模态（v2 明确口径）
- 文本 parts 直接入正文；图片/Canvas 等非字符串 parts 以 `[附件 n]` 占位入块（T04G 已实现），原文件若平台可下载则落 L1 附件区并登记 ID；
- 附件内容不进投影正文——与「模型不碰原始媒体」铁律一致（ZCode 413 事故教训）。

### 3.6 隐私与安全（不变项）
- L1 永不修改、永不入 git、永不外传；脱敏发生在 L2 卡层；捕获工具状态目录（.ai-chat-flow）与数据目录隔离。

## 四、v2 相对现状的增量工作量（评估）

| 项 | 工作量 | 说明 |
|---|---|---|
| 90_Inbox 目录+放行逻辑 | 半小时 | ingest 扩展平台字段+移动放行 |
| registry 主键升格（平台+ID） | 1 小时 | 一次性迁移脚本，旧条目补 source |
| 文件名规范执行 | 零 | 捕获时按规范命名即可，存量 12 文件重命名一次 |
| 衍生层退役 | 零 | 停止生成即可，存量不删 |
| 对账定时化 | 可选 | ZCode 定时任务跑 --scan+报告，导出仍人手 |

## 五、v2 不做什么（防止过度设计）

- 不写浏览器自动化去抓会话列表（平台风控+条款风险+脆弱）；
- 不做「实时流式」捕获（对话结束才有稳定内容）；
- 不引入第三方同步工具依赖（.ai-chat-flow 可继续用，但它只是捕获手段之一，规范不绑定它）；
- 不改投影层（已稳定）。

## 六、请 AC 重点审的三件事

1. **ChatGPT 平台侧还有没有更优的导出通道？** 例如：设置里按会话导出的选项、分享链接的完整度（分享页是否含全部轮次与图片）、Canvas/图表/文件附件在官方导出 conversations.json 里的呈现方式——AC 对平台功能的一手认知比我们测试全。

3. **官方 conversations.json 的字段盲区**：多模态消息、工具调用、被编辑/重新生成的分支在官方导出里如何表现？有没有我们 capture 路线拿不到、或官方导出反而缺失的内容（如记忆功能数据、Gizmo/自定义 GPT 配置）？
