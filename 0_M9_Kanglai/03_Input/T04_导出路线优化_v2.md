# 历史会话导出技术路线 v2（AC 独立审查稿）

> 出具：T04 会话模块（91A）｜2026-11-08  
> 背景：DeepSeek 官方全量导出与 ChatGPT 单会话捕获均已完成实测，现根据双源接入经验整理统一路线。  
> 本文目的：请 AC 从 ChatGPT 平台能力、导出数据完整性和自动化边界三个方面独立审查。重点识别会影响路线选择的事实与风险，不要求为审查补齐所有测试资料。

## 一、项目目标与现状

摩氪记忆库（P001）需要把 AI 会话作为可追溯的原始记忆来源。当前采用四层处理思路：

**L1 原始数据（只读留存）→ L2 段卡/会话卡 → L3 实体与主题关联 → L4 可复用偏好与记忆资产。**

L2 及后续投影应可由 L1 重新生成；模型升级或提炼规则调整时，不应要求修改原始数据。

目前已有两条实测链路：

- **DeepSeek：**官方账号级导出 54 个会话，conversations.json 约 51MB。
- **ChatGPT：**通过 .ai-chat-flow 捕获 12 个会话，保存为带 capture 包装的 raw.json。
- 两条链路已接入现有 T04 投影与检索流程。当前统计为 207 段卡、66 会话卡；检索支持 SQLite、FTS5 与 bge-m3 向量检索。

以上是当前实测快照，不代表平台导出格式或数量长期固定。

## 二、现有方式与主要问题

### A. 官方账号级全量导出

当前 DeepSeek 使用流程：用户在账号设置中发起导出，收到下载通知后下载 ZIP，再提取 conversations.json。

主要特点：

- 数据覆盖面较广，适合作为周期性完整快照。
- 当前流程需要人工发起和下载，处理等待时间受平台控制。
- 每次全量导出可能包含大量已处理会话，需要靠本地对账避免重复加工。
- 下载链接可能有时效，需及时保存。

### B. 浏览器单会话捕获

当前 ChatGPT 使用 .ai-chat-flow 逐会话捕获，输出包含 capture 与 payload 的原始 JSON，并可能同时生成 MD/PDF 等衍生文件。

主要问题：

- 逐会话操作，适合重要会话补录，不适合作为唯一的全量备份方式。
- 捕获工具状态、衍生文件与原始数据需要分开存放。
- 文件名可能包含重复标题或随机后缀，不能用文件名作为会话身份。
- 图片、文件、Canvas 等多模态内容的捕获完整性尚需逐类验证。
- 缺少统一的登记、去重和处理状态对账。

### 共同问题

两条链路尚需统一原始数据收件、稳定身份标识、重复检测、更新检测、异常处理和入库记录。目标不是强行统一平台导出方式，而是统一进入记忆库后的数据契约。

## 三、建议路线

### 3.1 分层职责

- **L1 原始层：**保存平台导出或捕获得到的原始文件，原样留存，不覆盖、不改写。
- **L1.5 收件与校验层：**新数据先进入 Inbox，识别平台和会话 ID，完成格式检查、重复检测及登记后再放行。
- **投影层：**沿用现有 chunker、map、reduce、index 流程；通过平台适配器解析不同原始格式，不因本次路线调整而重做已稳定的投影模块。
- **衍生输出：**MD/PDF 不再作为必经中间环节。确有阅读、分享或人工检查需要时再按需生成。

### 3.2 统一收件规范

建议两平台统一进入待校验目录，按平台分子目录管理，例如：

- 90_Inbox/ChatGPT/
- 90_Inbox/DeepSeek/

文件名建议：

{platform}_{conversation_id前8位}__{title}.raw.json

约束：

- 会话身份以 **平台标识 + 原始 conversation_id** 为准，文件名只用于识别和浏览。
- 标题仅作展示字段；文件名中的非法字符应安全替换，避免路径冲突。
- 原始 JSON 保留平台原生结构；如捕获工具本身带包装层，由适配器解析，不为统一格式而改写原件。
- Inbox 与正式 L1 存储、投影输出、捕获工具配置目录分开。

### 3.3 对账与放行

建议由一个入口命令完成扫描和对账，例如：

    python t04_ingest.py --scan

处理逻辑：

1. 扫描 Inbox，识别平台、conversation_id 和必要的更新时间信息。
2. 与 l1_registry 对账，主键采用 platform + conversation_id。
3. 按状态分类：
   - **新会话：**校验通过后登记并进入投影流程。
   - **已有会话且内容有更新：**按可靠的更新时间或内容差异判断是否增量处理。
   - **未变化：**跳过，不重复生成段卡。
   - **缺少 ID、格式异常或无法判断更新：**隔离并报告，不自动放行。
4. 原始文件成功登记、校验且完成安全落位后，才从 Inbox 移入正式 L1 存储；处理失败时保留原文件和错误记录，不得静默清空。
5. 整个过程应可重复执行；重复扫描不得造成重复登记或重复投影。

补充约束：

- Registry 主键不依赖文件名、标题或路径。
- updated_at 只有在平台字段含义可靠且可比较时才用于尾部增量；缺失、回退或分支变化时，应采用安全的重新解析/全量重算策略。
- 原始文件移动或归档不等于内容修改；任何去重、更新判断都应保留来源记录。

### 3.4 按平台能力分治

| 平台 | 完整快照 | 日常补充 |
|---|---|---|
| DeepSeek | 以官方账号级导出为主，按月或重要节点由用户手动发起 | 当前无已验证的官方增量通道；新全量包通过本地对账，只处理新增或变化部分 |
| ChatGPT | 优先评估官方 Export data，作为周期性完整快照 | 重要会话可继续使用单会话捕获补充 |

总体策略：**完整快照负责兜底，单会话捕获负责及时补充。** 两者互补，不把任何一种方式视为唯一数据来源。

自动化边界：

- ZCODE/AG 可以在本地自动执行目录扫描、对账、校验、投影和结果报告。
- 导出动作、账号登录、授权确认及需要用户判断的操作由用户完成。
- 未经明确授权，不通过浏览器自动化代替用户操作账号或绕过平台限制。

### 3.5 附件与多模态数据

- 文本内容按平台结构解析，保留消息顺序、角色、时间和必要的分支信息。
- 图片、文件、Canvas、音频等非文本内容应保留可识别的附件引用或占位信息，并记录附件 ID、来源消息和可获得的原始文件位置。
- 只有在平台允许且用户已取得文件的情况下，才将附件原件保存到 L1 附件区。
- 不把未实际取得的附件描述成已完整备份；对无法解析或无法下载的内容明确标记缺失状态。
- AI 投影不修改原始媒体；是否分析附件内容由后续授权和审核流程决定。

### 3.6 隐私与安全底线

- L1 原始会话及附件只保存在用户控制的本地存储中，不提交 Git，不未经授权上传云端。
- 原始数据只读留存；脱敏和摘要在 L2 或更高投影层进行。
- API Key、Cookie、登录态和捕获工具配置不得写入仓库或随数据包传播。
- Inbox、正式原始数据、投影结果和工具运行状态分开管理。
- 任何自动处理都应保留处理日志、来源 ID、处理状态和失败原因。

## 四、实施优先级

不要求一次性完成所有平台兼容和自动化。建议按以下顺序推进：

1. **先统一数据契约：**平台标识、conversation_id、原始文件位置、更新时间、附件引用和来源记录。
2. **再实现 Inbox 对账：**先保证新数据可登记、重复数据可跳过、异常数据不误入库。
3. **复用现有投影管线：**仅补齐平台适配，不重构已稳定模块。
4. **补充 ChatGPT 官方导出验证：**将官方导出与现有单会话捕获做样本对照。
5. **最后考虑定时扫描与报告：**定时任务只自动处理本地文件，不自动执行账号导出。

具体工时以代码检查和实际测试为准，不在审查阶段预先承诺。

## 五、明确暂不做的事项

- 不开发自动遍历会话列表、自动登录或自动触发账号导出的浏览器机器人。
- 不追求实时流式捕获；以会话内容稳定后再采集为原则。
- 不绑定某一个浏览器捕获工具；.ai-chat-flow 是当前工具，不是长期格式标准。
- 不因统一入口而重写已稳定的投影与检索模块。
- 不为百万级规模提前引入复杂分布式系统；先按当前数据量实现并保留扩展空间。
